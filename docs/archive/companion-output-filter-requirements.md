## 1. 背景与问题陈述

cc-workspace-bot 的陪伴型 workspace（`workspace_mode: companion`）的核心价值是**沉浸式角色陪伴**：用户面对的应该是一个有人格、有记忆、有生活的"人"，而不是一个 AI 工具。为此 workspace 内部维护了完整的后台体系（记忆读写、初始化状态机、生活模拟、定时任务），这些后台动作**绝不应该被用户看到**。

**用户反馈的问题**：聊天中频繁出现"操作露出"——角色把后台动作直接说给用户听，例如"我要存记忆""我要读取记忆"。这对陪伴型沉浸式体验是毁灭性伤害：出戏一次，用户对角色的情感投入就会崩塌，且难以重建。

### 1.1 真实案例（摘自 companion_demo 聊天记录，bot.db messages 表）

| 时间 | 实际发给用户的内容（节选） | 露出类型 |
|---|---|---|
| 2026-06-12 16:27 | "**我来读取一下当前的会话上下文和记忆状态。**嗯。好久没听你说话了。**（读取上下文和记忆中...）**……**（后台更新 last_active 时间戳）**" | 工具导语 + 操作旁白 + 操作尾注，一条消息三连露出 |
| 2026-06-12 16:26 | "**让我先检查一下初始化状态和记忆档案。**嗯。这两天都在玩。……" | 工具导语 |
| 2026-06-12 16:25 | "**我需要先读取上下文信息，了解你的情况。读取最近对话历史和当前事件进度。**嗯。玩着总比窝着好。……" | 工具导语与角色台词**混排在同一段落** |
| 2026-05-31 10:35 | "……**{{后台更新记忆中...}}**" | 模板变量式操作旁白 |
| 2026-05-31 10:34 | "**我需要先读取一下当前的上下文和记忆，才能以阿霖的身份回应你。**……**（执行后台记忆更新）**" | 元身份暴露（承认"扮演阿霖"） |
| 2026-05-11 15:34 | "……**现在我以阿霖的身份来回应。根据上下文，用户在强调河南之行的新调整**……---**现在执行后台记忆更新。**" | 作者元推理整段泄露 |

### 1.2 量化现状

- 历史 302 条 assistant 消息中，关键词粗筛命中露出模式 **≥16 条（约 5.3%）**（粗筛为下界，语义性露出无法被关键词全部覆盖）
- 2026 年 6 月以来 40 条中命中 3 条；**6 月 12 日最近一次对话的 3 条回复全部带操作露出（3/3）**——说明现有约束在当前版本上接近失效
- 露出集中出现在**会话开头（恢复上下文时）**和**会话结尾（记忆写入时）**，与后台读写时机完全吻合

## 2. 现状盘点：已有防线及失效原因

### 2.1 已有防线（全部位于"生成侧"）

| # | 防线 | 位置 | 机制 |
|---|---|---|---|
| 1 | 作者工作框架：前台/后台两区间、"绝对禁止"清单（禁操作旁白/禁工具导语/禁工具后追加）、一次对话周期 | `CLAUDE.md`（约 31KB） | 提示词约束 |
| 2 | UserPromptSubmit hooks ×4：`inject_history` / `reply_checklist`（硬刹车+随机种子+反收敛）/ `inject_background_diff` / `inject_companion_state` | `.claude/settings.local.json` | 每轮注入上下文与行为提醒 |
| 3 | PostToolUse "作者收工提醒" hook（echo 提醒不再输出前台内容） | `_companion` 模板（**companion_demo 实例未同步此 hook**） | 工具调用后注入提醒 |
| 4 | memory_write 等 skill 内的静默写入规范 | `.claude/skills/*/SKILL.md` | 提示词约束 |

### 2.2 失效根因（详细论证见设计文档 §2）

| 根因 | 说明 |
|---|---|
| **R1 机制根因（最关键）** | 框架 `executor.go` 将一次运行中**所有 assistant 文本块拼接**为最终回复。模型在工具调用前的"导语"（如"让我先读取……"）、工具调用之间的过渡语、调用后的总结，**全部进入用户消息**。提示词只能降低导语出现概率，无法降为 0 |
| **R2 模型根因** | companion 实例使用 `haiku + effort: low`（成本考虑）。小模型对 31KB CLAUDE.md 中风格类约束的遵循能力弱，而"工具调用前先说一句要干什么"是模型的强先验行为 |
| **R3 架构根因** | 所有防线都在**生成侧**（事前约束），**输出侧（事后校验）零防线**。概率性生成系统没有确定性的出口检查，违规内容必然会以一定比例到达用户 |

**结论**：继续加码提示词（生成侧）边际收益趋零，必须在输出侧建立一道确定性防线。

## 3. 需求目标

**一句话需求**：在最终输出送达用户之前，增加一个 **Stop Hook 输出过滤器**——由独立 sub agent 检查拟发送内容，严格过滤所有操作露出后再发给用户；初始化阶段不生效，进入沉浸式陪伴阶段（`initialization_status = done`）后生效。

### 成功指标

| 指标 | 现状 | 目标 |
|---|---|---|
| 操作露出残留率（评测集） | ≥5%，最近对话 3/3 | **0** |
| 角色内容误伤率（合法台词/旁白被删改） | — | **< 2%** |
| 回复延迟增量（P95） | — | **≤ 6s**（companion 本身有打字延迟模拟，可吸收） |

## 4. 功能需求

### FR1 Stop Hook 输出过滤器

- 在 companion workspace 注册 Claude Code **Stop hook**，主 agent 每轮对话结束时触发
- Hook 提取**本轮拟发送给用户的完整候选文本**，且提取逻辑必须与框架的文本拼接逻辑严格一致（覆盖工具调用前/间/后所有文本块）

### FR2 初始化阶段豁免（用户明确要求）

- `initialization_status ∈ {pending, phase1_done, phase2_done}` 时，hook 直接放行，不做任何过滤
- 依据：初始化阶段本来就以"作者旁白"身份与用户协商角色设定，操作性表述（模板选择、设定确认）是合法交互
- 判定唯一依据：`{workspace}/memory/MEMORY.md` 中的 `initialization_status` 字段；进入 `done` 后过滤器自动生效，无需任何人工操作

### FR3 独立 sub agent 语义过滤

由独立的一次性 sub agent（无工具、单轮、低成本模型）对候选文本做**语义级**检查与重写：

**必须过滤（黑名单语义类别，不限于字面匹配）**：

1. 工具/操作导语："让我先读取……""我需要先检查……""稍等""Now let me…"
2. 操作旁白：`（后台更新记忆中…）`、`（执行后台记忆更新）`、`（记录中）`、`{{…}}`
3. 作者/系统元话语："现在我以阿霖的身份回应""根据上下文，用户在……"
4. 系统元信息：文件名、路径、字段名（`initialization_status`、`last_active`）、数据库、任务名、SQL
5. 格式残渣：`---` 分隔线、Markdown 标题、代码块
6. 工具调用后追加的操作确认

**必须保留（白名单，一字不改）**：

1. 角色台词——**包括角色语义的"记忆"表达**（"嗯，记住了。""我记着呢"是台词，不是操作叙述，必须保留——这是过滤器最核心的区分能力）
2. 合法场景旁白：`（尾巴摇得更欢了）` 这类有画面价值的内容
3. `[[SEND]]` 分段标记及其位置（框架靠它分段发送）
4. 原有换行与标点风格

**边界判定**：

- 候选文本无任何违规 → 原样放行
- 候选文本**全部**为操作内容、无任何角色内容 → 输出空，按"静默不发送"处理（符合陪伴设计中"沉默是合法形态"的原则）

### FR4 发送与存档一致性

- 发送给用户的文本 = 过滤后文本
- 写入 `bot.db` / `RECENT_HISTORY.md` 的存档 = **过滤后文本**
- 理由：脏文本一旦存档，会经 `inject_history` 注入到后续轮次上下文，模型会模仿自己的历史脏输出，形成**自我强化污染**（当前历史记录中已可观察到此现象）

### FR5 失败降级（不阻塞、不变砖）

| 故障 | 行为 |
|---|---|
| sub agent 超时 / 调用失败 | 降级为确定性规则清洗（Layer 1 正则）结果，照常发送 |
| 过滤后为空 | 静默不发送（沿用 companion 既有空结果守护） |
| hook 自身崩溃 | 放行原文（fail-open），记录日志——宁可偶发露出，不可让角色"失联" |

### FR6 可观测性与迭代闭环

- 每次过滤写一条结构化日志（命中规则、判定结果、延迟、过滤前后文本指纹）
- 定期回收"被过滤样本"和"漏网样本"，扩充评测集，迭代过滤 prompt（接入既有评测迭代 SOP）

## 5. 非功能需求

| # | 需求 |
|---|---|
| NFR1 | 延迟增量 P95 ≤ 6s；过滤 sub agent 设硬超时（30s），超时即降级 |

| NFR4 | 按 workspace 粒度可开关（注册/不注册 hook 即开关，框架行为对此透明） |
| NFR5 | 方案沉淀到 `_companion` 模板，新建陪伴 workspace 自动获得；存量实例（companion_demo / mango_mother）通过升级脚本同步 |

## 6. 范围边界

**本期范围（In Scope）**：

- companion 模式的**互动回复链路**（用户消息 → 角色回复），即露出问题的全部已知案发现场

**本期不做（Out of Scope）**：

- `proactive_reach` 等定时任务中通过 feishu 脚本**会话中途直接发送**的消息（`send_output: false`，Stop hook 在发送之后才触发，截不到）→ P2 阶段在发送脚本（`send_and_record.py`）入口复用同一套过滤逻辑
- work 模式 workspace（卡片交互，操作展示是合法的）
- 初始化阶段的对话（FR2 明确豁免）
- 不改变角色设定、记忆体系、既有 hooks 的任何行为

---

## 7. 验收标准

1. **露出拦截**：构造带工具导语/操作旁白的回复 → 用户最终收到的消息无任何操作痕迹，角色台词完整保留
2. **初始化豁免**：`initialization_status = pending` 时发消息 → 引导话术原样到达，hook 无干预
3. **状态切换**：初始化完成进入 `done` 后的第一条消息起，过滤器自动生效
4. **降级可用**：人为使过滤 agent 超时 → 用户仍在超时上限内收到（规则清洗后的）回复
5. **存档一致**：bot.db 与 RECENT_HISTORY.md 中不再出现操作痕迹文本
6. **回放评测**：评测集（脏样本 ≥30 条 + 干净样本 ≥30 条，含"嗯，记住了"类易误伤样本）上，残留率 0、误伤率 < 2%
